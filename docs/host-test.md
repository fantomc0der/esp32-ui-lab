# The host build: testing the C layer without a board

`firmware/host-test/` compiles the binding layer for the machine you are sitting at, links it against stubs for the Arduino surface, and runs it under AddressSanitizer and UndefinedBehaviorSanitizer. It exists because everything correctness-critical in `firmware/lvgl-js-bindings/` was previously verified only by `app/selftest.js`, which runs on the panel and reports over serial — so CI never compiled a line of the C layer, and a memory bug waited until somebody flashed a board.

The two use-after-frees this repo has actually hit are the argument for it. A stale widget handle written through, and a trampoline dropping the last reference to a closure it was mid-call on (both in [`runtime-architecture.md`](runtime-architecture.md)) are precisely the class of bug a sanitizer catches on every commit and a human reading a serial log does not. Both are now regression cases in `tests/test_ownership.cpp`.

## Running it

Needs a C++17 compiler, CMake ≥ 3.22 and Ninja. Nothing else: LVGL is fetched by the build, QuickJS is already vendored, and no display libraries are involved.

```bash
cd firmware/host-test
cmake -S . -B .build -G Ninja
cmake --build .build -j
cd .build && ctest --output-on-failure
```

The first configure clones LVGL 9.5.0, so it needs network and takes a minute; after that a full rebuild is seconds. `.build/` is gitignored.

On Windows, where the repo is normally developed, there is no system compiler. A container is the path of least resistance and matches what CI runs:

```powershell
podman run --rm -v "${PWD}:/w" -w /w ubuntu:24.04 bash -lc `
  "apt-get update -qq && apt-get install -y -qq build-essential cmake ninja-build git && cmake -S firmware/host-test -B /tmp/b -G Ninja && cmake --build /tmp/b -j && ctest --test-dir /tmp/b --output-on-failure"
```

Building into `/tmp/b` rather than into the mount keeps the object tree inside the container, so a Linux build tree is not left behind in a Windows working copy. Drop the `-B`/`--test-dir` overrides if you would rather keep it (it is gitignored either way).

## What is covered

Four suites, one binary each so that a crash under ASan still lets the others report:

- **`test_ownership`** — the JSValue lifetime rules from `jsvm_core.cpp`. The self-stopping timer and the stale widget handle, in both their write and read forms; the two different release paths for event bindings (the `LV_EVENT_DELETE` hook for a child, `jsvm_stop()`'s sweep for the screen object itself); timers left running at teardown; and a double `.stop()`, which is a double free if `timer_release()` stops nulling the wrapper's opaque. The layer has two trampolines with the same hazard on each, so the event one is covered alongside the timer one: a click handler that calls `lv.screen().clean()` is deleting the widget LVGL is mid-dispatch to, which frees the binding holding the closure that is running. Deleting the `fn` dup that guards against it is a `heap-use-after-free` inside `JS_CallInternal`, with `free_function_bytecode` on the freeing stack. Reaching any of this needs `lv_obj_send_event()` from the suite's C side, because every name in `kEvents` is a code only an input device raises and the harness registers none. The companion `widget` dup is a different matter and is in the limits list below, because on the one shape that could observe it a bytecode callee has already copied the argument into its own frame.
- **`test_props`** — `apply_props` and the string→enum tables from `bindings_lv.cpp`. The one that earns its place is the ordering rule: `value` is applied twice, because it is read before `options` exists and LVGL clamps a selection against an empty list to zero, so `{options, value}` in a single call would otherwise always land on item 0. Also colours in all three accepted forms, percentage/pixel/content sizes, range clamping, unknown props degrading rather than throwing, and the widget-kind guard in both directions. The alignment, flex-flow and flex-align tables are checked by *position* rather than by not throwing — `apply_props` ignores a name it does not recognise, so a dropped or misspelled entry is invisible to a `try`/`catch` — with the two exceptions noted below. All three assert geometry rather than only a count of distinct places, because distinctness alone would miss a table whose entries were *permuted* rather than dropped: swapping two codes leaves the count unchanged. That claim is measured rather than argued — every transposition within each of the three tables was applied in turn and the suite fails on all 57.
- **`test_reload`** — start and stop the same script 25 times and assert the heap returns exactly to where it began, in both bytes and block count. This is the test the issue asked for first, and the reason is procedural: reload correctness was checked by hand, five cycles at a time, by watching a serial log. It also covers teardown after a script that throws half-way, and `jsvm_start()` called repeatedly with no intervening `jsvm_stop()`, which is what `sys.launch()` ends up doing.
- **`test_modules`** — `sys` and `fs`. Both are compiled in, so leaving them unasserted would have meant shipping code the target builds and never exercises. Covers the three host hooks (including `NAN` surfacing to scripts as `null`, which is how the real board reports a battery reading it cannot take while the radio holds ADC2), backlight clamping at each bound separately, every way a percent can fail to be a number throwing rather than dimming the panel to its floor (`null` and the booleans among them, which JavaScript would convert to 0 and 1, and a boxed `Number` or a `BigInt`, which are not numbers by tag), alongside the values that must still get through so the rejection has not widened into a legal call, the pin being read from storage and written through to it, and the `flash:` prefix addressing a different filesystem from the same path space.

The pin is worth a note, because the obvious test of it does not work. `bindings_sys.cpp` caches the pin in a file-static that nothing resets, since on a device the process starts once — so after any `sys.pin()`, every later `sys.pinned()` in the same process is answered from that cache. A test shaped as "pin it, restart the VM, read it back" therefore passes with storage entirely disconnected, which was verified by gutting `Preferences::putString` and watching all four assertions still pass. What the suite does instead is seed the store before anything has read it (the state a device that already had a pin boots into), and check the write half against the store directly rather than through `sys.pinned()`.

Two independent leak checks run over all of it, and they overlap less than "belt and braces" suggests. `host_heap_live_bytes()` counts allocations made through `heap_caps_*`, so it sees a `JS_DupValue` that was never released, and it sees it at the end of the cycle rather than at exit. LeakSanitizer sees anything unreachable when the process ends whatever allocator made it, which makes it the only check that notices an `EventBinding` or `TimerBinding` leak — those come from plain `malloc` (`jsvm_core.cpp:197` and `:253`). Two cases fall between them, and both are worth knowing before trusting a green reload run. A binding left linked on `g_events` is `malloc`-side, so invisible to the counters, and still reachable from a global, so not a leak by LSan's definition — what catches that one is the JSValues it still holds, which the counters do see. An LVGL object left attached to the display is invisible to both for the same pair of reasons: under `LV_STDLIB_CLIB` LVGL allocates through plain `malloc` rather than the shim, and a widget still parented to a live display is reachable at exit. So a reload leak on the LVGL side, as opposed to the JS side, is not something this suite would report.

Every serial assertion goes through one of two helpers — `check_printed()` for a value read back through the REPL, `expect_output()` for one a script printed as it ran — and both match the trailing newline rather than doing a bare substring search. That is not fussiness: a substring search made "this timer fired once" pass while the timer was firing ten times, because `b=1` is a prefix of `b=10`. Only the right edge is anchored, so a key that is a suffix of another key would still collide; nothing does today, and anchoring the left edge is not safe because an exception's stack trace is printed without a trailing newline.

The build type is `Debug` with `-O1`, and deliberately not `RelWithDebInfo`. That preset is `-O2 -g -DNDEBUG`, and the `NDEBUG` compiles out all 139 `assert()`s in `quickjs.c` — including `assert(p->ref_count > 0)` on the GC's decref path, the cheapest detector available for an over-released `JSValue`. Trading that away for `-O2` would be a poor deal in a suite that finishes in half a second either way.

## What it does not cover, and will not

Nothing here says anything about hardware. The panel, touch, PSRAM capabilities, SPI DMA and FreeRTOS task behaviour are all absent by construction, and `app/selftest.js` on a real board remains the acceptance test. Specifically:

- **The flush path is a no-op.** The byte-swap invariant (`lv_draw_sw_rgb565_swap()` paired with `draw16bitBeRGBBitmap()`) is display-side and cannot be tested here. Rendering runs; the pixels are discarded.
- **`heap_caps_*` maps onto `malloc`, and the capability flags are ignored.** That is the point — it puts every allocation where ASan can see it — but it means a host run cannot tell you whether something would have fitted in real PSRAM or in DMA-capable internal RAM. The free-size numbers the layer prints are synthetic. Never read them as a memory measurement.
- **A small underflow through a `heap_caps_*` pointer is the shim's blind spot.** The accounting header sits immediately *before* the address handed out, so writing just before a block hits that header rather than ASan's left redzone. The corruption is silent at the time and surfaces later as an unexplained byte mismatch in `test_reload`. If a reload assertion ever fails for no visible reason, suspect this before suspecting the leak logic. An overflow past the end is caught normally.
- **Colours cannot be verified, only accepted.** The binding exposes no style getter, so a script cannot read a colour back. The `parse_color` cases assert that all three accepted forms (`"#ff8800"`, `"ff8800"`, `0xff8800`) parse without throwing and leave a live widget, and nothing more: making `parse_color()` return `false` unconditionally leaves them passing. Whether the right pixels light up is a panel question.
- **`align: "top-left"` cannot be verified, only accepted.** The other eight names in the alignment table are checked by position — each must place a child somewhere no other name does, so a dropped or misspelled entry fails. `LV_ALIGN_TOP_LEFT` puts a child exactly where an unaligned child already sits (15,15 in the test's box; padding shifts both identically), so that one name going missing is indistinguishable from it working. Comparing against a deliberately unrecognised name fails for the same reason. Distinguishing it would need the binding to report an alignment back, which it does not.
- **`flexAlign: "start"` cannot be verified either, for the same structural reason.** The other five names in `kFlexAligns` are checked by where they leave three children in a row, but `start` is also the value `apply_props` initialises to before consulting the table, so an unmatched name lands on it. That one entry going missing is indistinguishable from it working; the other five are not.
- **The event trampoline's `widget` dup cannot be covered from here, though its `fn` dup is.** Deleting the `fn` dup is a heap-use-after-free inside `JS_CallInternal`, caught by the self-cleaning-handler case. Deleting the `widget` dup and its matching `JS_FreeValue` leaves every assertion green, and the reason is stronger than "the outcomes coincide": in the case that would see it, nothing goes wrong. `JS_Call` always passes `JS_CALL_FLAG_COPY_ARGV` (`quickjs.c:20378`), so the condition at `:17632` holds whatever `argc` is, and a bytecode callee copies its arguments into its own frame at `:17655` — one `js_dup` per argument actually passed, capped at the declared count (`n = min_int(argc, b->arg_count)` at `:17652`, with any remaining declared slots filled with `JS_UNDEFINED` rather than duped). That case's handler declares `self`, so it holds a reference for the frame's lifetime and the binding dropping its own reference mid-handler takes the refcount to 1 rather than to 0. Measured, not inferred: with the dup removed, a handler that deletes its widget and then churns 20000 allocations still reads `self` with no sanitizer report. What *is* caught is deleting the dup alone and leaving the free, which is an over-release, reported by ASan from `JS_FreeRuntime`'s GC.

  The scope of that protection is narrower than it first looks, which is the argument for keeping the dup. The copy is sized by the callee's declared parameter count (`arg_allocated_size = b->arg_count` at `:17633`, gated at `:17651`), so a handler declaring no parameters gets no copy at all and `arg_buf` stays the borrowed `argv` from `:17645`. And it is bytecode-only: `:17620-17628` hands `argv` straight to `call_func` for a native or bound-to-native callable, which `.on()` accepts. Neither shape reads its widget after triggering a delete today, so the mutation survives either way and this stays uncoverable — but the dup is what makes surviving a property of the trampoline rather than of whichever handler a script happens to define.
- **An LVGL-side reload leak is invisible to both leak checks.** Under `LV_STDLIB_CLIB` LVGL allocates through plain `malloc` rather than the shim, so it is outside `host_heap_live_bytes()`, and a widget still parented to a live display is reachable at exit, so LSan does not count it either. `test_reload` covers the JS side of teardown, not the LVGL side.
- **There is no input device**, so `lv_indev_active()` is always null and the event trampoline's `fn(widget, x, y)` branch is unreachable here. Its `fn(widget)` branch is not: `lv_obj_send_event()` from a test's C side enters the trampoline exactly as LVGL's own widgets do when they raise an event outside a touch, which is what `test_ownership` uses to cover the dup pair. Synthesizing touch to reach the other branch would mean inventing coordinates the panel never produced, so the coordinate path stays a hardware question.
- **Timing is virtual.** `millis()` and LVGL's tick both come from a counter the tests step explicitly, which makes "this timer fired twice" exact instead of racing wall-clock time. It is not a claim about scheduling on the device.

## Two deliberate scope decisions

**`jsvm_app.cpp` is not compiled.** The supervisor is written against Arduino `String`, `Serial.available()`/`read()` and `File.print()`. Stubbing those is a larger surface than every other stub combined, and it is the surface most likely to rot. The issue scoped the first pass to `jsvm_core.cpp` plus `bindings_lv.cpp` for that reason. The path resolution it also lists (`loadScript`/`resolveFs`, the `flash:` prefix, the card-then-flash fallback) is the obvious next addition, and the in-memory `fs::FS` stub already exists to support it — what is missing is only an Arduino `String` and a line-reader on the Serial stub.

**Wi-Fi is compiled out (`JSVM_WITH_WIFI=0`).** `WiFi.h`, `HTTPClient.h` and `NetworkClientSecure.h` are the largest stub surface in the layer and the least meaningful without a network. `sys` and `fs` *are* compiled in and covered by `test_modules`, because their stubs are small and genuinely behave: the filesystem is a real in-memory one, and `Preferences` is a real key-value store that outlives any single handle the way NVS outlives the one that opened it.

Where a stub could plausibly be more forgiving than the real API, it is not. `Preferences::getString` refuses rather than truncates when the value does not fit its buffer, matching the device, because truncating would hand a caller a shortened path that looks valid and hide on the host a bug that would bite on the board. The same reasoning applies to `heap_caps_get_free_size` and friends returning `uint32_t`: `size_t` is 32-bit on the ESP32, so the layer's `%u` format strings are correct there, and declaring these `size_t` on a 64-bit host would produce `-Wformat` warnings on firmware code that is not wrong.

A consequence worth stating: **`app/selftest.js` cannot currently run as the host test body**, which the issue floated as the cheapest way to get coverage. It makes five `wifi.status()` calls and eighteen `sys.*`/`fs.*` calls, so with Wi-Fi compiled out it would fail on the binding surface rather than on behaviour. Compiling Wi-Fi in — or teaching the host `wifi` module to report a permanent "no radio" — is what would unlock sharing that one file between both targets. It remains the right end state, and it is not free.

## The stub layer, and how it rots

`stubs/` is the cost centre. Every `#include <Arduino.h>`-ism the C layer grows later needs something here, and a stub that drifts from the real API is worse than no stub because it compiles.

Two things keep it honest. The stubs mirror the real include graph rather than being a convenience header — `Arduino.h` pulls in `esp_heap_caps.h` because the ESP32 core's does, and `bindings_fs.cpp` relies on exactly that. And the host `lv_conf.h` **includes the board's copy** instead of duplicating it, overriding only the four settings the host needs differently, so which widgets exist and which fonts a script may select are physically the same values the panel builds with. A host test cannot pass against a configuration the board does not run.

That include names `boards/waveshare-s3-touch-147/` outright, as does `host_harness.cpp` for `SCREEN_W`/`SCREEN_H`. With one board that is the honest thing to write rather than a premature abstraction. A second board would turn those two paths into a CMake option selecting which board directory to build against — the tests themselves need no change, since they assert relationships and percentages rather than pixel counts, apart from the one case that reads a literal 120 px width.

The override that matters is `LV_USE_STDLIB_MALLOC` → `LV_STDLIB_CLIB`. LVGL's builtin allocator is a pool it manages itself, so ASan would see one large `malloc` and none of the widget allocations inside it; routing LVGL onto the C library's `malloc` is what makes a widget-level use-after-free visible. `LV_USE_ASSERT_OBJ` is also turned on, which the board leaves off because it costs a check on every object access. It adds no coverage for the stale-handle cases in `test_ownership` — those throw a `TypeError` from `jsvm_arg_widget()`'s validation before LVGL is handed the object at all — but it is free here and backstops a binding added later that forgets to validate. Be exact about what that backstop is, because it is not the assert firing: `LV_ASSERT_OBJ` calls `lv_obj_has_class()` before `lv_obj_is_valid()`, and that dereferences the pointer, so on a freed handle ASan reports the read from inside LVGL and the assert never runs. The value is a report at the first LVGL entry point rather than wherever the freed object was next touched; on a type mismatch against live memory the assert itself fires and names the problem.

## In CI

The `host-test` job in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every push, and is one of the checks the ruleset requires to merge, alongside `scripts`, `firmware` and `review`. So a suite that fails here blocks the merge rather than merely reporting. That required set lives in GitHub settings rather than in the repo, so no diff can establish it and this sentence can go stale without anything failing: [`pr-automation.md`](pr-automation.md) records the whole expected configuration and how to read the ruleset back, and is the place to check when the gate behaves unexpectedly.
